# Task: Refactor Wedding RSVP Data Model and Implement Invite-Code-Specific Form Flows

## Context

This project is a static website with a wedding RSVP feature. Google Sheets serves as the backend, and a Google Apps Script web app processes POST submissions, appends data to a spreadsheet, and dispatches an email notification.

Review all attached code references before making changes:

1. Frontend RSVP form UI, including the `rsvp-form` flow.
2. Google Apps Script backend responsible for recording submissions and sending email notifications.
3. JavaScript responsible for invite-code validation, form state, and POST submission.
4. Any relevant CSS, shared components, configuration, or tests.

The current spreadsheet schema is:

`timestamp,email,name,extras,invite_code`

The `extras` field is an integer representing the number of additional guests accompanying the primary `name`.

## Objectives

Implement two coordinated changes:

1. Replace the `name` + `extras` spreadsheet model with an explicit list of party-member names.
2. Refactor the `rsvp-form` UI into a two-stage flow that first requests an invitation code, then presents the appropriate RSVP form based on that code.

Keep the implementation minimal and consistent with the existing static-site architecture. Do not introduce a frontend framework, third-party dependency, database, or unnecessary abstractions.

# Part 1: Invite-Code-Specific RSVP Flow

## 1. Supported invitation codes

The frontend must recognize exactly these two valid invitation codes:

- `271117`
- `74774`

Both codes must be accepted. Do not replace the existing code with the new one or accidentally make either code invalid.

Use the existing invitation-code validation mechanism where practical, but ensure the new two-stage UI works correctly.

The invitation code determines which RSVP form the user can access.

## 2. Refactor the `rsvp-form` flow

Replace the current direct-to-form experience with a two-stage flow.

### Stage 1: Invitation-code entry

Initially, display only an invitation-code entry interface.

The initial view should:
- Prompt the user to enter their RSVP/invitation code.
- Provide a clearly labeled input and a Continue button.
- Validate the code against the two supported values.
- Display a clear, accessible error message for invalid codes.
- Keep the user on the code-entry screen when validation fails.
- Transition to the correct RSVP form when validation succeeds.
- Avoid displaying either RSVP form before a valid code is entered.
- Preserve the existing design system, styling conventions, responsiveness, and accessibility.

Normalize input appropriately, such as trimming surrounding whitespace. Do not silently accept arbitrary codes or use partial matching.

### Stage 2: Render the form associated with the code

After successful validation, render the appropriate form based on the validated invitation code.

Implement the following exact routing logic:

| Invitation code | Form behavior |
|---|---|
| `271117` | Display a dedicated RSVP form that does not allow extra guests. |
| `74774` | Display the existing RSVP form, preserving its existing extra-guest functionality. |

The two form experiences must be distinct in behavior, even if they share reusable components.

Do not simply add or remove a field visually while leaving the underlying form submission logic unchanged. The submitted data must reflect the restrictions associated with the validated invitation code.

## 3. Form behavior for code `271117`

This code must open an RSVP form that does not allow extras.

Requirements:
- Collect the primary invitee's name.
- Do not display an extras count, additional-guest selector, or add-guest control.
- Do not permit the user to add extra party members through this form.
- Submit exactly one party member in `party_names`.
- Ensure the submitted invitation code is `271117`.
- Preserve the existing email field, validation, RSVP controls, and other relevant form behavior.
- Do not change unrelated wedding RSVP business rules.

The resulting logical party data should contain exactly one name, represented as a one-element array in the frontend before serialization.

Example:

```javascript
const partyNames = ["Alex Smith"];
```

The backend payload should contain:

```javascript
{
  email: "alex@example.com",
  party_names: "Alex Smith",
  invite_code: "271117"
}
```

The example illustrates the required data structure, not a requirement to hardcode these values.

The restriction must be enforced in the frontend's state and submission logic, not just through hidden or disabled UI controls.

## 4. Form behavior for code `74774`

This code must open the existing RSVP form with its current extra-guest functionality.

Requirements:
- Preserve the existing form's extra-guest controls and intended behavior.
- Allow the user to identify the primary invitee and the additional guests according to the existing UI's conventions.
- Convert the resulting party members into an explicit list of names.
- Submit every party member's name in `party_names`.
- Ensure the submitted invitation code is `74774`.
- Preserve all other existing validation, submission states, RSVP controls, success/error messages, and email-related behavior.

Do not redesign this form unnecessarily. Reuse the existing UI and business logic as much as possible.

### Important distinction

The old `extras` integer must no longer be sent to the backend or stored in the spreadsheet.

For code `74774`, preserve the user-facing ability to specify extra guests, but translate that input into actual party-member names.

If the current implementation only collects a count of extra guests and does not collect their names, inspect the existing UI and implement the smallest necessary change to collect each additional guest's name individually.

Do not invent placeholder names for extra guests. A party member must have an actual, valid name before submission.

For code `271117`, extra guests must remain prohibited regardless of any stale or manipulated frontend state.

## 5. Invitation-code integrity and state management

Treat the invitation code validated during Stage 1 as the source of truth for the active form.

Requirements:
- Store the validated code in application state and use it to select the correct form.
- Do not allow the user to change the active form's invitation code by modifying an unrelated form field.
- Ensure the code submitted to the backend is the validated code, not an arbitrary value supplied by the form.
- Reset or clear relevant form state when the user returns to the code-entry screen or starts a new RSVP flow.
- Ensure switching between codes, restarting the flow, and failed validation
