# Agent Prompt: Refactor RSVP Flows to Use Predictive Guest Search and Individual Attendance Selection

## Objective

Refactor the existing static wedding RSVP website to replace manual party-member entry with a predictive text guest-search flow powered by `output.json`.

The new flow must identify the invitee's party from a selected guest name, display every member of that party as an individual row, collect an attendance decision for each person, and submit only attending guests in the `party_names` field sent to the existing backend.

Before making changes, inspect the existing project files, RSVP components, styles, frontend JavaScript, Google Apps Script backend, and any existing invitation-code logic. Use the linked `output.json` as the authoritative dataset for predictive search and party membership.

Do not rebuild unrelated parts of the website or remove existing functionality that is not explicitly being replaced.

## 1. Required User Flow

Implement the following sequential flow:

1. **Invitation code:** The user enters their invitation code.
2. **Predictive guest search:** After the code is validated, display a predictive text field for searching guest names.
3. **Party resolution:** When the user selects a matching guest from the suggestions, derive their entire party from `output.json`.
4. **Party display:** Show every member of the selected party as a separate row.
5. **Individual attendance selection:** Each member's row includes two mutually exclusive choices:
   - `Will attend`
   - `Will not attend`
6. **Submission:** Build the `party_names` list from only the members marked `Will attend`, then submit the RSVP to the existing backend.

The user must select a suggested guest rather than merely typing a name and submitting it. Do not infer the party from arbitrary, unvalidated text.

## 2. Invitation Codes and Existing Form Behavior

Preserve the two existing invitation codes and their established routing:

- **`271117`:** Single-invitee flow. Do not allow the user to RSVP for additional guests outside the party identified by the selected name. Resolve the selected name to the corresponding party data, but enforce any single-person restriction already associated with this code.
- **`74774`:** Existing group RSVP flow. Allow the user to review all members of the party associated with the selected guest and choose an attendance response for each member.

Treat the invitation code as a required step before guest search becomes available.

Use the existing code-validation mechanism wherever possible. Do not introduce conflicting validation logic or expose private RSVP data before the code has been validated.

If the current code restrictions and the party structure in `output.json` conflict, inspect the existing implementation and resolve the discrepancy explicitly rather than silently changing the established invitation rules.

Validate invitation codes and submitted party membership on the backend as well as in the frontend wherever the current architecture supports it. Hiding UI elements alone is not sufficient enforcement.

## 3. `output.json` Dataset

`output.json` will be linked in Copilot and is the authoritative source for the guest-search options and party membership.

Example:
```json
[
  {
    "Guest": "Bill",
    "Guest1": "Denice"
  },
  {
    "Guest": "Greg",
    "Guest1": "Michelle"
  }
]
```

Interpret each JSON object as one party. Each nonempty guest value in that object represents one member of that party.

In the example:
- Bill and Denice belong to the same party.
- Greg and Michelle belong to the same party.

The property names (`Guest`, `Guest1`, and potentially additional numbered fields) are column labels, not guest names. The values are the guest names.

### Dataset requirements

- Load and parse the dataset using the existing project's conventions.
- Do not hardcode the example names or assume that every party contains exactly two members.
- Support objects containing different numbers of guest fields.
- Ignore null, undefined, empty, or whitespace-only guest values.
- Trim leading and trailing whitespace when normalizing names.
- Preserve the original display spelling of names from the dataset.
- Handle an empty or malformed dataset gracefully, showing a useful error rather than breaking the page.
- Do not silently merge distinct parties that happen to share a name. Detect duplicate normalized guest names and handle them explicitly.

### Build a normalized internal representation

Create a reusable data-processing function that transforms each dataset object into a party containing its valid members. Each member should retain their original display name and a stable reference to their party.

For example, the data above could produce a structure conceptually equivalent to:

```javascript
[
  {
    partyId: 0,
    members: ["Bill", "Denice"]
  },
  {
    partyId: 1,
    members: ["Greg", "Michelle"]
  }
]
```

This is illustrative; follow the existing project's coding conventions and choose an appropriate stable party identifier.

Build the predictive-search options from this normalized representation. Each option must map unambiguously to a member and their complete party.

## 4. Predictive Text Search

Implement a reusable, accessible predictive-search component for the guest-name field.

### Behavior

- Display a text input with suggestions as the user types.
- Match guest names case-insensitively.
- Ignore leading and trailing whitespace during matching.
- Support partial-name matching.
- Sort and group the source dataset as supplied; do not mutate the source dataset.
- Display suggestions using the original spelling of the guest names.
- Selecting a suggestion must retain the corresponding member-to-party mapping, not just the text string.
- After a guest is selected, display their party.
- Do not resolve a party from a partially typed name without a deliberate selection.
- If there are no matches, display a clear `No guests found` message.
- Handle duplicate names explicitly, for example by showing a distinguishing party label if one can be derived safely. Never select an arbitrary party when a name maps to multiple parties.
- After a guest is selected, prevent stale suggestions or stale party data from affecting the submission.
- If the user changes their search after selecting a guest, clear the previous selection and its attendance answers until a new valid guest is selected.

### Accessibility

- Associate a visible label with the input.
- Support keyboard navigation through suggestions using the arrow keys.
- Support Enter to select the highlighted suggestion and Escape to close the suggestion list.
- Use appropriate combobox/listbox semantics and active-descendant relationships where practical.
- Ensure the search and suggestions remain usable on mobile.
- Do not rely on color alone to communicate the selected option.

## 5. Party Member Attendance UI

Once a guest has been selected, render a row for every valid member of the selected party.

Each row must display the member's name and two mutually exclusive attendance options:

- `Will attend`
- `Will not attend`

Use accessible radio buttons or an equivalent mutually exclusive control. Style the controls to fit the existing website rather than introducing an unrelated design system.

### State and interaction rules

- Every member must have an explicit attendance answer before the RSVP can be submitted.
- Do not preselect `Will attend` or `Will not attend` unless the existing project has a documented requirement to do so.
- Changing one member's answer must not change any other member's answer.
- Selecting a different guest must reset the attendance answers for the newly selected party.
- The selected party's members must be displayed in the order in which they appear in the corresponding `output.json` object.
- Do not allow users to add arbitrary guest names or members who are not present in the resolved party.
- Display clear validation feedback if one or more members lack an answer.

For invitation code `271117`, enforce the existing single-invitee restriction. For `74774`, show the full resolved party.

## 6. Constructing `party_names`

The backend expects a `party_names` field containing the names of the guests who will attend.

Build the submitted list from the attendance answers, not from the entire party and not from a numeric guest count.

For example, given the party:

| Guest | Answer |
|---|---|
| Bill | Will attend |
| Denice | Will not attend |
| Alex | Will attend |

The attending list must be:

```javascript
["Bill", "Alex"]
```

When preparing the backend payload, serialize the list as newline-delimited names:

```javascript
const partyNames = selectedParty.members
  .filter(member => attendance[member.id] === true)
  .map(member => member.name);

const payload = {
  invite_code: validatedInviteCode,
  party_names: partyNames.join("\n")
};
```

The example assumes each member has a stable `id` and that attendance is represented as a boolean. Adapt the code to the project's actual state structure.

### Submission rules

- `Will attend` maps to `true`.
- `Will not attend` maps to `false`.
- Only `true` members are included in `party_names`.
- Preserve each attending member's original display name and party order.
- Do not include non-attending guests in `party_names`.
- Do not send arbitrary guest names.
- Do not derive attendance from whether a name is present in the search field.
- Do not submit until every displayed member has an explicit answer.
- If nobody will attend, submit an empty `party_names` value only if the existing backend and RSVP business rules support an all-declined response. Inspect the current implementation and preserve or implement the appropriate explicit behavior.
- Ensure the selected party and invite code correspond to the same validated RSVP session.

Keep the payload compatible with the current Google Apps Script endpoint and its expected field names. Do not rename backend fields without updating all dependent code.

## 7. Backend and Google Sheets Compatibility

Inspect the existing Google Apps Script before changing the frontend submission logic.

Preserve the current backend behavior, including timestamp creation, spreadsheet insertion, and email notifications.

The expected spreadsheet structure remains:

`timestamp, email, party_names, invite_code`

Each RSVP submission should create one row representing the responding party. Store the attending names in `party_names`, separated by newline characters inside a single cell.

Verify that the backend:
- Accepts the existing form's expected request format.
- Handles newline-delimited `party_names` correctly.
- Validates the invitation code and guest membership to the extent possible using trusted server-side data.
- Does not trust arbitrary party names or a client-supplied party ID without verifying the mapping.
- Enforces any invitation-specific restrictions.
- Handles empty attending lists according to the existing RSVP rules.
- Preserves email notification functionality.
- Returns or propagates submission errors so the frontend can display appropriate feedback.

If backend validation requires access to `output.json`, determine the safest way to make the dataset available to the backend. Do not assume that a static website's local JSON file is automatically accessible from Google Apps Script.

If the frontend and backend cannot share the dataset directly, document a reliable validation strategy and implement it consistently with the existing architecture.

## 8. Submission and Error States

The refactored form must provide clear feedback for these cases:

- Invalid invitation code.
- Empty search query.
- No matching guest.
- Ambiguous duplicate guest name.
- No guest selected from the suggestions.
- Missing attendance answer for one or more party members.
- No attendees selected, if prohibited by the existing business rules.
- Dataset load or parsing failure.
- Backend submission failure.
- Successful submission.

During submission:
- Disable duplicate submissions.
- Show an appropriate loading or progress state.
- Preserve the user's answers if submission fails.
- Display a success confirmation only after the backend reports success.
- Prevent stale or duplicate form submissions.

Do not log unnecessary guest or RSVP data to the browser console.

## 9. Code Quality and Scope

- Keep the invitation-code step, predictive search, party display, and submission logic clearly separated.
- Keep the normalized dataset and guest-to-party lookup reusable.
- Avoid unnecessary dependencies for a static website.
- Do not introduce a build system or framework unless the project already uses one.
- Avoid unrelated layout, typography, animation, or design changes.
- Maintain responsive behavior and existing wedding-site styling.
- Remove obsolete extras-count controls and logic only where they are replaced by this new flow.
- Keep unrelated RSVP fields, such as email, if they are currently required by the backend.

## 11. Acceptance Tests

The implementation is complete only when all applicable tests pass:

1. Entering an invalid invitation code does not reveal guest search.
2. Entering `271117` opens the appropriate restricted RSVP flow.
3. Entering `74774` opens the group RSVP flow.
4. Typing a partial guest name displays matching suggestions.
5. Selecting a suggestion resolves the correct complete party.
6. Each party member appears in an individual row with both attendance options.
7. The user cannot submit without answering for every displayed member.
8. Changing a member from attending to not attending removes them from `party_names`.
9. Changing a member from not attending to attending adds them to `party_names`.
10. Attending names are newline-delimited and stored in a single spreadsheet cell.
11. The selected guest's full party is resolved from `output.json`, not hardcoded.
12. Duplicate names cannot silently resolve to the wrong party.
13. Editing the search after selection clears stale party and attendance state.
14. Failed submissions preserve the user's answers and display an error.
15. Successful submissions preserve spreadsheet insertion and email notification behavior.
16. Invitation-specific restrictions are enforced by the backend wherever possible.
17. The form works on mobile and supports keyboard and screen-reader interaction.

**Final priority:** correctness of guest-to-party resolution, accuracy of individual attendance choices, integrity of the `party_names` payload, and compatibility with the existing backend take precedence over cosmetic changes.
